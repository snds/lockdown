# Import, export and backups

_Status: built, 2026-10-18, on branch `slice/import-export` (D122: desktop and web first; there is no web vault yet, so "web" here is nothing). The core reads eight other managers' files plus CXF, CSV and Lockdown's own backups; exports four ways; keeps crown jewels out unless the person opts an item in (D121); and writes scheduled, sealed backups to a folder. The desktop app has an Import wizard, an Export dialog, Backups in Settings and the per-item opt-in. The backup format is published at [`../format/backup-v1.md`](../format/backup-v1.md). Proposed decisions D135–D144 are at the end. Companion to [`10-desktop-shell.md`](10-desktop-shell.md) (the layers and the gates), [`02-model.md`](02-model.md) §3 and §11, [`04-security.md`](04-security.md) §10 and §15, and [`15-organization.md`](15-organization.md) (vaults, folders, tags)._

## For future agent

- **TL;DR:** Every file is parsed in the core (`lockdown-cxf`), size-capped and treated as hostile, into one item shape through one `Builder`; the person sees a preview (counts per kind, crown jewels, files, what can't come along) and then says yes. Exports are written by the core to a place the person picked in the operating system's own save dialog; the bytes never reach the webview. A crown jewel leaves in an export or a backup only when its "Include in exports and backups" is on, and turning that on asks for the account password. Backups are Lockdown's own sealed files (Argon2id, then XChaCha20-Poly1305 in 1 MiB chunks), written on a schedule while Lockdown is unlocked, the newest N kept.
- **Reads before this:** `10-desktop-shell.md` §2–§3, `02-model.md` §3, §6, §11, `15-organization.md`, decisions D101, D103, D121.
- **Not here:** the CLI (it still carries its own CXF/CSV import and has no export), the OS credential-exchange rows (deferred, D122), the emergency sheet, the duplicate finder after import (built by the organization slice as a separate view).

## 2. Formats and mappings

Every importer calls `lockdown_cxf::build::Builder`: a value for a kind's template field lands in it by id (`user`, `pw`, `url.N`, `code.N`, `card.*`, `wifi.*`, `bank.*`, `ssh.*`, …, `crates/vault/src/template.rs`) with the template's kind and label; dates and months are normalized (`YYYY-MM-DD`, `YYYY-MM`); a choice is matched to the template's options; a value the field can't hold, a second value for it, or a field the template lacks lands as a field of the person's own (`custom.N`) under the source's label, masked when the source marked it secret. One-time codes are checked (`otpauth://`, `steam://`, or a bare base32 secret made into a link); one that doesn't parse is reported, never kept half-read. The source's folder path becomes folders in the vault picked (made where missing), its tags and favourite the item's own (15-organization). Earlier passwords (1Password, Bitwarden) and KeePass's entry history become the item's earlier versions. Items in a source's trash are left out and counted.

**Hostile input.** Every file is size-capped (64 MiB; a backup 512 MiB); a ZIP is read under caps on entries (20,000), each entry and the total unpacked (256 MiB), and its paths are checked; every value over 64 KiB and every file over 32 MiB is left out and named; the reserved (`lockdown.*`) and filing (`org.*`) fields are stripped from anything not a Lockdown backup, so a file can't opt a crown jewel in or name a folder it never saw; a reader that panics on input nobody foresaw refuses the file instead of taking the app down. `crates/cxf/tests/importers.rs` feeds every sample file, cut at 24 points, with 40 sets of flipped bits and 10 garbage blobs, straight to each format's own reader with no safety net, and requires a value, never a panic.

**Sample files.** `crates/cxf/tests/fixtures/` holds one file per format shaped like the real export, every value made up (`src/` holds the readable insides of the ZIPs); the KeePass database and the password-protected Bitwarden file are written by an ignored test that remakes them. They were built from the formats as documented and as the open-source importers read them, not exported from the apps themselves; a check against real exports is open (§5).

## 3. Export, the opt-in and backups

**Export.** `Session::export_file(format, password, vault)`: `lockdown` (the backup format: plain without a password, sealed with one), `cxf` and `csv` (plain), `kdbx` (sealed; Argon2d at the desktop floor, one group per folder or kind, tags as tags, passkeys in KeePassXC's `KPEX_PASSKEY_*` fields, attachments). The preview says what the file will hold and lists what stays out: crown jewels not opted in, by title; for CXF the attachments and history; for CSV everything that isn't a login, passkeys, files, history; for KDBX history, match rules and kinds; items in Deleted except in the Lockdown format; files not yet on this device. A plain export needs `plain_confirmed`; every export goes through the `Reveal` gate. The shell opens the save dialog itself (`tauri-plugin-dialog`, from Rust only) and keeps the chosen place under a one-time number (`Picked`), so the webview can name a place but never make one up; the core writes the file readable by the person only, through a `.partial` file and a rename. The older `export_items` command, which handed the bytes to the webview, is gone.

**The opt-in (D121).** `lockdown.export`, a yes-or-no field sealed with the item's fields: signed, versioned, synced, never drawn as a field, kept by every edit without being named (the same reserved-field rule as the security center's `lockdown.security`). `set_export_opt_in` is a crown jewel's only; on goes through the `Reveal` gate (the account password where one exists), off asks nothing. The detail of a crown jewel shows the switch under the crown-jewel surface.

**Backups.** The person picks a folder (the OS dialog, held as above), how often and how many, and a backup password of at least 8 characters. Its Argon2id key is derived once and kept in `backup-key.cbor` beside the other data files, sealed under a key derived from the persona's App Data Key and bound to the vault's id, so a scheduled run needs no password while the vault is open and the kept key is useless without the vault. The worker's one-second tick writes a backup when one is due (never counted as activity; a failed run retries after 15 minutes), names it `lockdown-backup-YYYYMMDD-HHMMSS.lockdown`, and prunes the folder to the newest N **of files with that name only**. `set_settings` from the webview can't move or switch backups; only the gated `backup_setup` and `backup_off` change them. Restore lists the folder's backups and opens one with the kept key when it made it, else with the password, into the same preview as an import.

**Restore and merge.** A Lockdown backup keeps each item's id, class and state. Landing: an id not in the target vault comes back with its id; one that is there and the same (filing aside) is left; one that changed gets the backup's fields as a new version (history kept, files the item lacks added); one in Deleted here is left with a note; one purged here comes back as a new item. Folders come back with their ids; an item whose folder isn't in the backup comes back unfiled, with a note. Every earlier version is replayed as a version, signed by this device and dated today: the content of the history is kept, the original times are not (§5).

## 4. Choice of cipher (encrypted export)

Lockdown's own AEAD with Argon2id, not `age`: 02-model §11 already names Argon2id and XChaCha20-Poly1305 streaming; both crates are in the tree at the versions the identity crate uses, and the key-derivation floors are the identity crate's own (04-security §4), where `age`'s passphrase mode is scrypt with its own work factor. The construction is small enough to publish in a page and to reimplement with libsodium and any Argon2 library (`backup_format.rs` does exactly that). `age` remains the right tool for public-key recipients, proposed below as an addition with its own `kdf.alg`.

## 5. Gaps

- **Real-export verification**: the sample files follow the documented shapes; none was exported from the apps themselves. Before calling a format done in front of users, import one real export per app (Sean's own, or a throwaway account's) and add any field the samples missed.
- **Not read**: Proton's PGP-encrypted export, Bitwarden's account-locked export, 1Password's older `.1pif`, Dashlane's secure archive (`.dash`), passkeys from Proton and Keeper, Bitwarden attachments (not in its JSON).
- **History times**: replayed versions are dated at import; keeping the original times needs the vault to accept a version dated in the past (the organization slice's `carry_in` does for moves; a follow-up can route restores through it).
- **CXF**: Wi-Fi through CXF's own type; attachments in a CXF exchange container.
- **Backups**: run only while Lockdown is unlocked; no "last backup" line outside Settings; no emergency sheet; age-recipient backups.
- **CLI**: `lockdown import` still uses its own CXF/CSV copy and there is no `lockdown export`; moving the CLI onto `lockdown-app` covers both.
- **Web**: no web vault exists to carry any of this.

## 6. Host-contract gaps in unicron, found building this slice

1. No file input: the wizard uses a native `<input type="file">`, unstyled beside the system's fields.
2. No choice list (radio cards) for "what kind of file": a `NativeSelect` with a description under it stands in.
3. No new-password control (password, repeat, match and length check): two `Input`s and the shell's own check.
4. No wizard or stepper pattern: the dialog swaps its body per step.
5. A `FieldLabel` pointed at a `Button` renames the button for assistive tech; the folder row uses `FieldTitle` instead.
6. No byte-size or relative-time formatting for lists (the backups list): the shell formats them.
