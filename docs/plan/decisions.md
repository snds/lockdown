# Lockdown — decision log

_One line per decision. Proposed by the agent, approved by Sean unless marked. Newest at the bottom._

| ID | Date | Decision | Status |
|---|---|---|---|
| D1 | 2026-10-15 | **Positioning is all three layers at once.** A ("every way you sign in") is what a user feels; B ("can't betray you") is the proof; C ("open, fair, yours": open source, self-host, free export) is standing policy. One lead message per surface, never three slogans side by side. | Sean |
| D2 | 2026-10-15 | **Lockdown and Mailbird form an ecosystem but each works alone.** Neither app may require the other for any core job. Value rises when both are installed. "Works alone" is a release gate for every shared feature. | Sean |
| D3 | 2026-10-15 | **Shared profile and persona.** One identity contract (profile, personas, devices) that each app can use on its own or link to the other's. A persona in Mailbird and a persona in Lockdown can be the same persona or deliberately separate. Synapse already defines personas; the three products must share one schema, not three. | Sean (schema owner TBD) |
| D4 | 2026-10-15 | **Secure enclaves that authenticate each other.** Each app keeps its own enclave (keystore-backed). Apps attest to each other over an authenticated local channel (code-signature or process identity, per the NDSS-style IPC lesson) and can pass scoped grants, never raw master keys. | Sean |
| D5 | 2026-10-15 | **Shared secure notes with a Lockdown recovery path.** A note locked in Mailbird can be opened with the Lockdown master password or the Lockdown recovery kit (Secret Key + recovery code), the way 1Password's Emergency Kit works. Mechanism: Mailbird's locked-notes key is wrapped to the Lockdown identity key when the apps are linked. Mailbird keeps its own standalone lock (Phase 33) when not linked. | Sean |
| D6 | 2026-10-15 | **Plugin ecosystem is shared doctrine.** Both apps get a plugin model with the same risk tiers, signed manifests, consent gates and kill switch defined in the research brief §2.9. First-party plugins only at first. | Sean |
| D7 | 2026-10-15 | **Self-hosting is a value-add, not the default.** Cloud and self-host run the same server binary. A private-cloud bundle hosts Lockdown and Mailbird together. Mail server, DNS tooling and 3-2-1 backup live in Mailbird's scope; Lockdown contributes the identity, secrets and backup-encryption pieces and must itself be backup-friendly (encrypted, restorable, verifiable). | Sean |
| D8 | 2026-10-15 | **Non-passkey vendor bridges go to a "maybe" backlog.** Steam QR approval, trade confirmations, Battle.net imports and the like are parked. Steam-style codes (plain TOTP variants) stay, because they are standard code generation. TV/console device-code activation stays under review as a standards-based feature, not a vendor bridge. | Sean |
| D9 | 2026-10-15 | **Aim for the most feature-complete app from day one.** v1 targets parity across the full matrix, not a thin wedge. Tradeoff accepted: longer v1 and a larger team than the 6–8-engineer, 12–18-month plan in the brief; the plan set must re-estimate. | Sean |
| D10 | 2026-10-15 | **Any app can create the identity; the first one installed owns it until Lockdown adopts it.** Each app can create a login, identity and persona on its own, with no other app present. On first run an app detects an existing ecosystem install and piggybacks on that install's identity instead of creating a second one. When Lockdown arrives later it reads the existing identity and takes over *management* (recovery, device enrolment, sharing) without moving the data, changing its location, or re-encrypting it. The user's cost is: install, run once, done. Consequence: identity and key material must use one shared format from the first release of any app (a shared Rust crate), because "adopt without re-encrypting" is impossible otherwise. | Sean |
| D11 | 2026-10-15 | **The recovery kit is a property of the identity, not of the app that made it.** Whichever app first creates the recovery kit (Secret Key + recovery code) creates it for the shared identity. Any other ecosystem app, on any device, can open the identity's vault when given that kit. On the same device no kit is needed: the local handshake grants access. The kit is for a new device, or when no other app is present to vouch. Consequence: every app-level data key must be wrapped to the identity key from the start, or that data stays out of reach of the kit. | Sean |
| D12 | 2026-10-15 | **Mailbird is the test-bed for the identity and persona crate.** The shared crate is built inside Mailbird's Rust core first (it already has `crates/core`, a sync relay and the Phase 33 note lock as a first consumer), then extracted to its own repo once Lockdown needs it. Lockdown adopts it as reference implementation, never forks it. | Sean |
| D13 | 2026-10-15 | **Multiple personas per app, in every app.** Work, personal, business, or any combination, the way Synapse already models them. Each persona walls accounts, vaults, devices and mailboxes. Parked for detail; the identity crate must leave room for it from its first format version (persona is a first-class record, never a flag on the profile). | Sean (parked) |
| D14 | 2026-10-15 | **One shared design system across Mailbird, Synapse and Lockdown.** Mailbird's build (React 19, Vite, Tailwind v4, shadcn/ui on Base UI, Material Symbols) is the base. Synapse is rebuilt onto it. Lockdown starts from it. **Conflicts with Synapse D87 (approved the same day: "no shared registry; each project grows its own").** Needs Sean to confirm the reversal before Synapse changes course. | Proposed |
| D15 | 2026-10-15 | **Ecosystem identifier is neutral and domain-based, with no product name:** Apple App Group `group.design.snds.identity`; Windows and Linux shared folder under `snds/identity` (`%LOCALAPPDATA%\snds\identity`, `$XDG_DATA_HOME/snds/identity`); Android shares by signing key (D16). A brand rename never touches it. | Sean |
| D16 | 2026-10-15 | **One Android signing key for all ecosystem apps**, held in Play App Signing, so the identity store is shared by signature-level permission. Documented fallback if an app must leave the family: a bound service with a certificate-fingerprint allow-list. | Sean |
| D17 | 2026-10-15 | **Unicron is federated: contribution is open, ownership is not.** Consumers build in their app-extension layer, DSA flags candidates, consumers propose upstream PRs with a one-page spec and the DSA record, unicron code owners arbitrate against the uniqueness rule, releases are versioned with codemods for breaking changes. Published artifacts replace the submodule before a second consumer joins. Written up in `snds/unicron` `docs/06-contributing.md`. | Sean |
| D18 | 2026-10-16 | `Profile` carries `isk_pub` and the signed Argon2id params (`kdf`), so readers can verify the chain and refuse weak parameters on every load. Additive under §9. (From Mailbird PR #44.) | Sean |
| D19 | 2026-10-16 | ISK and persona receiving keys are **derived**, not stored: `ISK = HKDF-SHA-512(IRK, "ecosystem-identity/isk/v1")`; persona KEM seed `= HKDF-SHA-512(PK, "ecosystem-identity/persona-kem/v1" ‖ persona_id)`. Same reach as wrapping, no extra envelope. Rotation needs a counter field later. | Sean |
| D20 | 2026-10-16 | A Persona Key's `key_id` is its `persona_id`. | Sean |
| D21 | 2026-10-16 | Envelope file names are `<key_id>.<kind>.<id>.cbor`, because `wrapped_by` is a pair and the IRK has one wrap per device. | Sean |
| D22 | 2026-10-16 | `account` and `kit` wraps use the profile id as `KeyRef.id`. | Sean |
| D23 | 2026-10-16 | The hybrid KEM is X-Wing (`x25519-mlkem768`, RustCrypto `x-wing` over `ml-kem`), not an HPKE suite yet; the envelope `alg` `hpke-x25519-mlkem768` is defined and reserved. | Sean |
| D24 | 2026-10-16 | Every record is signed by the ISK; the "device key before the ISK exists" case never arises because the ISK derives from the IRK. | Sean |
| D25 | 2026-10-16 | `Device.kem_pub` and `EnrolledBy::Creator` are added (the spec named the enrolment pair but gave it no field, and the creating device had no `enrolled_by` value). | Sean |
| D26 | 2026-10-16 | **Accepted gap:** "Argon2id parameters only ever rise" is enforced across loads in a follow-up; the floor check alone is enough for the first implementation. Rollback head memory stays the caller's. | Sean |
| D27 | 2026-10-16 | **Division of the next crate steps:** Mailbird's session does spec §10 step 3 (re-wrap the Phase 33 note-lock key as Mailbird's App Data Key on next unlock), because it owns the notes store and the app's unlock flow; the Lockdown session does step 4 (the local handshake behind a test double) and the D26 follow-up, inside `crates/identity` only. No file overlap. | Sean (by "continue") |
| D28 | 2026-10-16 | **App label on App Data and Crown-Jewel envelopes,** bound into the AAD as well as the record, so a consumer can list its own keys (`app_keys(persona, app)`) and an envelope can never be re-labelled to another app. Requested by Mailbird's step-3 consumer. | Proposed |
| D29 | 2026-10-16 | **Envelope retirement:** `retire_envelope(key_id, wrapped_by)` deletes the file and writes a tombstone into the manifest chain, so stale wraps after a passphrase change do not accumulate and rollback detection still explains the deletion. | Proposed |
