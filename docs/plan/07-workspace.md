# The Rust workspace — v0.1 (as built)

_Status: as built, 2026-10-17 (first slice 2026-10-16; store, identity adoption and CLI, then the server and sync slice, the extension boundary, the recovery kit with cross-machine identity sync and device revocation, and the fifth slice, attachments and key transparency, 2026-10-17). Implements D35 over the crate table in `03-architecture.md` §2. Companion to `02-model.md` (what `vault` holds), `04-security.md` §3–§5 (what `crypto` must be), `01-identity.md` §10a–§10b (the crate we consume) and `09-extension-boundary.md` (what crosses into the browser)._

## For future agent

- **TL;DR:** One Cargo workspace, fourteen crates, one directory per row of the architecture table. Ten crates are real with tests (`crypto`, `matcher`, `codes`, `vault`, `cxf`, `store`, `sync`, `wasm`, `cli`, `server`); four are compile-clean skeletons that each carry the public types the plan names and one real rule under test. A vault round-trips through a plain SQLite file holding ciphertext only, opens from the ecosystem identity root and this device's keystore with no kit and no password (D10, D11), and syncs: the `lockdown` binary registers an account with OPAQUE, a second device enrols through that account, and two devices push, pull and merge against the one server binary, with conflict copies where the field-level merge cannot decide and "Rollback attempt blocked" when the server falls behind. Files ride along as attachments: 1 MiB chunks under per-file keys, named by ciphertext hash, pushed before the item and collected by the server once no key is left. The server keeps a public Merkle log of every identity manifest, vault head and device key it accepts, and every sync checks it: the tree head must continue the last one the device saw, the account's own entries must be the devices and heads the device knows, and the tree head is cited in every vault head so two devices catch a server that shows them different logs. The identity crate is a git dependency pinned by commit. CI runs fmt, clippy with warnings denied, tests and cargo-deny on Ubuntu and macOS, and builds the wasm and replays the clickjacking red team in Chromium.
- **Read with:** `03-architecture.md` §2 (the table this follows), `02-model.md` §12 (the sketches `vault` encodes), `decisions.md` D34–D82, `08-identity-proposal.md` (what the identity crate is asked to grow), `09-extension-boundary.md` (the matcher and wasm slice).
- **Do not:** copy anything out of `ecosystem-identity` into `lockdown-crypto` (D12), put a `todo!()` anywhere (use `Error::Unsupported` with a message), or add a dependency that `deny.toml` would refuse.

What the second slice settled (D39–D47; details in `decisions.md`):

- **The local store is a plain SQLite file holding ciphertext only** (03-architecture §11 q.1 decided). Four tables, every body canonical CBOR; the index lives in memory after unlock. What the file reveals: ids, sequence numbers, timestamps, sizes. What it never holds: a key, a title, a URL, a value.
- **The `Store` trait lives in `lockdown-vault`** (`vault::store`) and `lockdown-store` re-exports it, so `Vault::load(store, …)` and `Vault::save(store, adk)` take any backend without the vault crate depending on one.
- **Rollback memory is a separate file** (`HeadMemory`, `remembered.cbor`), never inside the vault file, so putting back an old copy of the vault file cannot put back the memory with it.
- **Load trusts nothing until it has checked the chain, the key and every item against the newest signed head.** The item header (kind, schema, class, device-only) is now under every version's signature and hash, because the load-time check showed a store could relabel an item otherwise.
- **Heads and versions are signed by the device keystore's key**, the one in the identity's `Device` record, through the `Signer` trait; other devices' heads verify against those records.
- **Lockdown's data lives beside the identity root** (`…/snds/lockdown` next to `…/snds/identity`): the device key file, the vault file, the memory file.

What the third slice settled (D49–D61; details in `decisions.md`):

- **Login is OPAQUE over ristretto255 with Argon2id at the desktop floor** on every device (D49); the account is a login name (D50); a login binds the device, and only bound devices may push heads or versions (D51).
- **The server orders, never reads.** It accepts a head only as the exact next page of the chain, naming its current head and listing only items it holds at those revisions (D53); it numbers item saves and hands a stale save back with its copy (D54). Everything it stores is what a device signed (D56).
- **Offline heads are provisional.** Sync replaces them with the server's chain and commits one head over the server revisions; item history is untouched (D55). Where two devices changed the same field, the server's value stays in the item and this device's version becomes a conflict copy named after the device and the day (D58).
- **Other devices are learned from the identity's own signatures**, relayed by the server, never from the server's word (D59, superseded by D71). The account slot was made without a Secret Key until the kit commands existed (D60, closed by D70).

What the fourth slice settled (D69–D74; details in `decisions.md`):

- **The recovery kit is real, and the Secret Key now protects the account slot.** `kit create` / `kit verify` / `recover` carry the 1Password-style flow (D69); the account slot is stretched with the kit's Secret Key through the crate's own `enable_account_unlock` (D70), and a slot written under D60 is upgraded on the next login with no format change — so a stolen server database plus the server key no longer allow an offline guess at the account password once a kit exists (closes D60).
- **The identity's records sync as a signed, server-ordered set**, not a last-write-wins blob: one hash-chained identity manifest the server can only extend, never rewrite, with every record signed by the Identity Signing Key (D71; `KnownDevices` → `SyncedIdentity`, closes §5 q.6 and narrows q.8).
- **A device can be revoked, and the revocation is enforced everywhere.** `device revoke` marks the record and names, per vault, the head after which that device's writes stop; the server and every client refuse a head, item or manifest it signs after that, while its earlier history still verifies, and a revocation never comes back (D73).
- **The ISK is borrowed through the crate's own functions** for the few record edits the crate has no call for, never re-implemented (D72); the CLI device name is `Lockdown on <hostname>` (D74). The asks for first-class crate support are `08-identity-proposal.md` §8.

What the fifth slice settled (D75–D82; details in `decisions.md`):

- **Attachments are chunked under per-file keys and named by their ciphertext.** 1 MiB chunks with the index and the count in every chunk's associated data, the plaintext padded to a size bucket, the file's name and size sealed beside the chunks, and the signed attachment list inside the item version (D75). Blobs sit in a `blobs` table of the vault file and of the server; the server takes a blob only under its own hash, only within its cap, keeps it only while some version still holds a key for it, and collects the rest after a day (D76). Sync pushes an item's blobs before the item and pulls them with it.
- **The server keeps a public, append-only log and the clients check it on every sync.** A BLAKE3 Merkle tree over every identity manifest, vault head and device key the server accepts, with signed tree heads and RFC 9162 proofs (D77). A device pins the log key, refuses a tree head that shrinks, forks or doesn't provably continue the last one it saw, audits its own account's entries against the devices and heads it knows, and stops before writing when anything disagrees (D78, D79). Every vault head cites the tree head its signer verified, so two devices catch a server that shows them two logs the moment they meet through the vault (D80). `lockdown audit` prints the account's log entries verified; `lockdown checkpoint` exports a signed page another device verifies (D81).

Two things the first slice changed in the model, both recorded in code comments:

- **Version signatures and hashes exclude the key envelopes** (`ItemVersion::without_keys`). Shredding a version destroys its wrapped key; if the signature covered the envelope, every purge would break history. The envelopes need no cover from the signature: each is sealed with associated data naming its place, and a swapped envelope yields a key that opens nothing.
- **The vault's key envelope is its own type** (`vault::keys::WrappedKey`), shaped like the identity crate's `KeyEnvelope` with the same refuse-by-place-before-decrypting rule, because the identity crate's `Purpose` and `KeyRefKind` stop at the App Data Key (02-model §13 q.2). The proposal to the crate owner is additive: `Purpose::{Vault, Item, Version, Attachment}` and `KeyRefKind::{Vault, Item, CrownJewel}`; when it lands, `keys.rs` becomes re-exports.

## 2. How identity is consumed

```toml
# Cargo.toml, [workspace.dependencies]
ecosystem-identity = { git = "https://github.com/snds/ecosystem-identity", rev = "96434d1de190164d7635302ce851fc0817000649", version = "0.1.0" }
```

- The crate was extracted from Mailbird `crates/identity` on 2026-10-16 (D34). It is pinned by **commit** because the `v0.1.0` tag push was being rejected by the git proxy when this was written; the line becomes `tag = "v0.1.0"` once the tag is on the remote. Mailbird's swap PR pins the same commit.
- `lockdown-crypto` depends on it directly and **re-exports** rather than mirrors: `kdf::{Argon2Params, FLOOR_DESKTOP, FLOOR_MOBILE, FLOOR_WASM, stretch, calibrate, hkdf_sha512}`, `kem::*`, `cbor::{to_canonical, from_slice}`, `auth::{AccountAuth, ExportKey, LocalStubAuth}`. The architecture table draws `identity → crypto`; as built it is `crypto → identity` until the crate exposes a primitives-only layer. Either way the constants have one home.
- `lockdown-vault` uses the identity crate's `Id`, `Timestamp`, `SymmetricKey`, `AppDataKey` and `CrownJewelKey` so a vault hangs off a persona's keys without conversion.
- Test speed: the identity crate's `insecure-test-kdf` feature lowers the Argon2id floor for debug tests. `lockdown-crypto` forwards it as its own feature of the same name, enabled only through its self dev-dependency. Never turn it on in an app.

## 3. CI matrix and guardrails

| Job | Where | Steps |
|---|---|---|
| `check` | `ubuntu-latest`, `macos-latest` | `cargo fmt --all --check` · `cargo clippy --workspace --all-targets -- -D warnings` · `cargo test --workspace` |
| `deny` | `ubuntu-latest` | `cargo deny check` (advisories, bans with `wildcards = "deny"`, licence allow-list, sources limited to crates.io and the identity repo) |

`RUSTFLAGS=-D warnings` is set for every step. `default-members` is every pure-Rust crate; `ffi` and `wasm` are built with the shells but compile on the host too, so `--workspace` covers all fourteen. Windows is not in the matrix yet: nothing platform-specific exists to test there, and the first Windows work (the COM passkey plug-in) needs an MSIX spike first (03-architecture §10).

Dependencies the third slice added: `opaque-ke` 4.0.1 (ristretto255 only; it brings a second copy of `sha2`, `digest` and `curve25519-dalek` until it moves to the current RustCrypto generation, which `deny.toml` warns on), `reqwest` 0.13 with `blocking` and `rustls-no-provider` plus `rustls` on the `ring` provider (no aws-lc build step), `clap`'s `env` feature and `tokio`'s `sync`/`signal` for the server. The licence allow-list grew by two permissive entries for that TLS stack: `ISC` (`ring` is "Apache-2.0 AND ISC", `rustls-webpki` is ISC) and `CDLA-Permissive-2.0` (`webpki-roots`' bundled Mozilla root store, via `rustls-platform-verifier`).

Local numbers on 2026-10-17, stable 1.97: 155 tests in the core crates and the two binaries, 168 with the desktop crate, all green (the CLI sync and kit end-to-end tests take about fifty seconds between them for the real Argon2id and OPAQUE rounds, the rest under two); clippy and fmt clean; `cargo deny check` → `advisories ok, bans ok, licenses ok, sources ok` with duplicate-version warnings only. The fourth slice added no dependency; `build-wasm.sh` now reads cargo's target directory from `cargo metadata` so a moved `CARGO_TARGET_DIR` builds, and the Playwright red team still passes six cases in Chromium. The fifth slice added no dependency either (`rusqlite` joins the CLI's dev-dependencies so one test can rewrite a server's log file between two clients).

## 5. Open questions raised by the build

1. Whether `lockdown-crypto` should keep depending on the whole identity crate (it pulls `schemars`, `serde_json`, `uuid`, `libc`) or the identity crate should split a `-primitives` crate the two can share. Harmless now; matters for the WASM binary size.
2. `Credential::Other` passthrough keeps unknown CXF credential types byte-for-byte on a CXF→CXF round trip, but a CXF→vault→CXF trip drops them with a report. Whether to store the raw JSON as a `custom` field so nothing is ever dropped.
3. The lookalike edit-distance rule (labels of six or more characters at distance one) will have false positives between unrelated real sites. Keep as a hard stop, or downgrade to a confirmation when the candidate has a valid certificate chain the extension can see.
4. `Vault::save` rewrites every item of the vault on every save (one transaction in SQLite). Fine for a CLI; a desktop vault with thousands of items wants dirty tracking per item. Also `trashed_at` is the one item field outside every signature; it only times the grace period, but the attachment step should fold it into the header or drop it from the item.
5. The identity crate lists app keys (`app_keys`) but not crown-jewel keys; Lockdown filters `envelopes()` by hand. Asked for in `08-identity-proposal.md` §5.
6. ~~`device_keys` trusts every device in the identity's records, revoked or not… Refusing a revoked device's *new* heads needs an order between devices only the server sees.~~ **Closed (D73).** `device revoke` names, per vault, the head after which the device's writes stop (the server's current head when the revocation is written); the server refuses anything it signs after that (`revoked_device`) and `check_revocations` refuses it on load and pull, while history before the boundary still verifies.
7. Whether Lockdown's device keystore file should be the same file another ecosystem app on the device uses (one `Device` record per machine) or one per app, as now (one per app per machine). The identity crate's `FileKeystore` sits in "the app's data directory"; the handshake (§6 step 3) assumes separate devices per app. Worth settling before the Mailbird link.
8. ~~The identity backup on the server is one blob, last write wins (D59).~~ **Closed (D71).** The backup is now a hash-chained manifest the server accepts only as the exact next page, so two devices can't both win: the second to push is told `fork` and pulls, merges and re-signs first. A revocation written on one machine reaches another on its next sync and is enforced there (D73). Still open within this: the chain is per account with no key-transparency checkpoint yet (step 9 above); two machines offline at once still serialise cleanly when they reconnect, one after the other.
9. Session tokens have no refresh (D52): every eight hours a device logs in again with the password. The shells will want a device-bound refresh credential so the password is typed once per device, not once per shift.
10. Every item push carries the item's whole history (D54). Fine at CLI scale; a long-lived login with hundreds of versions wants a "versions since" push, and the server's `items` table then needs a per-version row.
11. Sync squashes offline heads into one (D55), so the server's chain shows one head per sync per device rather than one per edit. The per-edit history is in the item versions, so the audit story holds; whether the chain should keep the finer grain for the activity log is a product call.
12. OPAQUE's stretching step is the desktop floor on every device (D49). A phone at 64 MiB and 4 lanes is at the edge of the uncertain mobile floor in 04-security §4; the device lab for q.2 there decides whether the suite pins a lower common floor or the slot moves to a per-profile signed parameter.
13. The login name is free text (D50). Whether it must be an email address (verification, recovery mail, the Mailbird link) is Sean's call before the first real sign-up.
14. The audit refuses a device key the identity's records don't list (D78). A device that logged in but hasn't yet pushed the identity manifest naming it trips this for the second between the two calls, and a device that logged in and then died before pushing trips it for good, which is the right alarm (someone with the password enrolled nothing) but a confusing one. Whether the enrolment flow should push the record before the first login lands, or the audit should grade this "warn once, refuse on the next sync", is worth settling with the first shell.
15. Blobs live in the vault's SQLite file (D76). Fine up to the server's 64 MiB cap; a desktop with gigabytes of scans wants them beside the file, and the server wants object storage (03-architecture §5). Both are a `Store`/`Storage` backend change, not a format change; the cap and the day's grace are Sean's numbers to confirm.
16. The server recomputes the Merkle root and every proof from all leaf hashes on each request (D77). Fast at thousands of leaves, wrong at millions; a cached tree is an implementation change behind the same endpoints. The log is also one per server, not one per account: an account's entries are served only to its sessions, but the tree size and the index of an entry leak how busy a server is.
17. Conflict copies (D58) carry fields, not attachments: a copy of an item with a file has the text but not the file (the original keeps it). Whether a copy should re-list the same blobs under the same Attachment Keys (cheap, since the keys are wrapped under the Item Key, which would have to be re-wrapped) is a product call.
18. ~~The desktop shell's command layer (`lockdown-app`) synced through `sync_vault` and `bootstrap_vault`, with no key-transparency session, while the CLI checked the log before and after every sync.~~ **Closed 2026-10-17.** `App::sync` and the first pull after a join now begin a `KtSession` from the shared `transparency.cbor`, audit with `lockdown_sync::DeviceExpectations` (moved out of the CLI so the two can't drift) and pass the session to `sync_vault_with` / `bootstrap_vault_with`; a refusal is `{ code: "refused" }` with the audit's words, and the Status screen shows the verified view. `ServerView` gained `checked_at` (defaulted, so older files read) for the "checked <time>" line.
